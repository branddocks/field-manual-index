You're typing code. You pause for half a second. Grey text appears — completing your function, writing the next 5 lines, sometimes an entire implementation. You hit Tab. It's exactly what you wanted.

How?

AI coding assistants like GitHub Copilot, Cursor, and Codeium aren't just chatbots pasted into your editor. They use fundamentally different techniques from ChatGPT — fill-in-the-middle completion, language server integration, codebase-wide context retrieval, and speculative edits that predict what you'll do next.

The result feels like magic. The engineering behind it is wild. Let's break it all down.

Fill-in-the-Middle: The Core Trick

ChatGPT generates left-to-right. Given text before the cursor, it predicts what comes after.

Coding assistants do something different: fill-in-the-middle (FIM). Given text BEFORE the cursor AND text AFTER the cursor, they predict what goes IN BETWEEN.

Left-to-right (ChatGPT-style) only sees:

"def calculate_total(items):\n "

Has NO IDEA the function should return 'total'

Fill-in-the-middle sees:

PREFIX: "def calculate_total(items):\n "

SUFFIX: "\n return total"

→ Must generate something that makes sense BETWEEN these

The model is trained with a special format:

def calculate_total(items):

example
code
<|fim_suffix|>
    return total<|fim_middle|>total = sum(item.price * item.quantity for item in items)

Why this matters enormously:

The suffix gives crucial context about what the code should DO

Variable names used later constrain what's generated now

Function signatures and return types guide the implementation

It reduces hallucination — the model can't invent random variable names because the suffix uses specific ones

Without FIM, the model might generate:

python

snippet
code
def calculate_total(items):
result = 0
    for item in items:
        result += item.cost  # Wrong variable name!
    return result  # Wrong return variable!

With FIM, it knows total is used later and generates accordingly.

Context Gathering: How It Knows Your Codebase

The biggest challenge for AI coding assistants isn't generation — it's context. Your cursor is in one file, but the relevant code might be in 20 other files.

The Context Window Problem

A model has limited context (128K tokens typically). Your codebase might be millions of tokens. What goes in the prompt?

Available context budget: ~8K-16K tokens (for fast completions)

What needs to fit:

├── Current file (around cursor) ~2K tokens

├── Imports and dependencies ~1K tokens

├── Related functions in other files ~3K tokens

├── Type definitions / interfaces ~1K tokens

├── Recent edit history ~500 tokens

├── LSP information (errors, types) ~500 tokens

└── Repository-level context ~500 tokens

How Context Is Gathered

Step 1: Nearby code — The most relevant code is the code around your cursor. Current function, current file, imports.

Step 2: Language Server Protocol (LSP) integration — This is where it gets sophisticated. Your editor already has a language server that understands your code's structure:

LSP provides:

├── Type information: "items is List[OrderItem]"

├── Function signatures: "OrderItem.price: float, OrderItem.quantity: int"

├── Error diagnostics: "TypeError on line 42: expected str, got int"

├── Symbol definitions: "total is referenced in return statement on line 15"

├── Import graph: "This file imports from utils.py, models.py"

└── Call hierarchy: "calculate_total is called by process_order in orders.py"

The coding assistant uses LSP data to find exactly which other files matter:

Step 3: Embedding-based retrieval — Cursor indexes your entire codebase as embeddings. When you're writing code, it searches for semantically similar code chunks — even if they're in files you haven't opened.

This is essentially RAG for code (Episode 22), and it's why Cursor feels like it "understands" your project.

The Completion Pipeline

Here's what happens in the ~200ms between you pausing and seeing a suggestion:

  1. Trigger detected (you paused typing for ~300ms)

│

  1. Context gathered (current file + LSP + embeddings) ~50ms

│

  1. FIM prompt constructed

│ [context + code before cursor] │ [code after cursor] │

│

  1. Sent to model (local or API) ~100ms

│ - Copilot: GitHub's cloud (Codex/GPT-4)

│ - Cursor: Mix of cloud + local models

│ - Codeium: Their optimized inference

│

  1. Response tokens generated (usually 1-10 lines) ~50ms

│

  1. Post-processing ~10ms

│ - Validate syntax (AST parsing)

│ - Check bracket matching

│ - Apply indentation rules

│ - Trim to logical boundary (don't stop mid-expression)

│

  1. Ghost text rendered in editor

Total time: ~200-400ms — fast enough to feel instantaneous after a natural typing pause.

Why Speed Matters

Completion needs to be FAST. If it takes more than 500ms, it arrives after you've already started typing the next character, and it's useless.

This is why coding assistants use:

Smaller, faster models for basic completions (not GPT-4)

Speculative decoding to speed up generation

Aggressive caching — if the context hasn't changed much, reuse the previous KV cache

Cancellation — if you start typing, cancel the in-flight request immediately

Cursor's key innovation: The Composer feature. Instead of completing one line at a time, you describe a change in natural language, and it edits multiple files simultaneously:

User: "Add error handling to all API routes and log errors to Sentry"

Cursor Composer:

├── Modifies routes/users.js (adds try-catch)

├── Modifies routes/orders.js (adds try-catch)

├── Modifies routes/products.js (adds try-catch)

├── Creates lib/error-handler.js (shared error handling)

└── Updates package.json (adds @sentry/node)

This is fundamentally different from completion — it's code transformation at project scale.

Under the Hood: The Models

GitHub Copilot

Originally used OpenAI Codex (a GPT-3 fine-tuned on code). Now uses a mix:

Fast completions: Custom small model (~1-3B params)

Complex completions: GPT-4-mini

Chat: GPT-4o

Cursor

Uses a mix of models:

Fast completions: Custom model (rumored ~3B)

Complex suggestions: Claude 3.5 Sonnet or GPT-4

Composer: Claude 3.5 Sonnet (excels at multi-file edits)

Embeddings: Custom embedding model for codebase indexing

Code-Specific Training

These models are fine-tuned on massive code datasets:

The Stack — 6.4TB of permissively licensed code from GitHub

StarCoder training data — 1T tokens of code in 86 languages

Code review data — PR comments, code reviews, bug fixes

Documentation — READMEs, API docs, StackOverflow

The fine-tuning isn't just "learn to write code." It includes:

Fill-in-the-middle training (the FIM objective)

Instruction following for code tasks

Bug detection and fix generation

Code explanation and documentation

Practical Takeaways

Fill-in-the-middle is the key innovation — knowing what comes AFTER the cursor is as important as what comes before

Context gathering is 80% of the magic — LSP integration, codebase embeddings, and recent edits determine suggestion quality

Speed matters more than perfection — a 200ms decent suggestion beats a 2-second perfect one for inline completions

Cursor's Composer is a paradigm shift — multi-file edits from natural language descriptions change how you code

The "Tab flow" is intentional — models predict your intent, not just the next token

Privacy tradeoffs are real — cloud models are better, but your code leaves your machine
